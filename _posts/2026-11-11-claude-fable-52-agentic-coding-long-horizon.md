這週我注意到一個讓我再次打開 Claude Code 文件頁面的更新：Anthropic 在 2026 年 11 月 9 日正式推出 Claude Fable 5.2，並且同步將它設定為 Claude Code 的預設模型。這不只是一次普通的模型升級——Fable 5.2 配備了 1M Token 的上下文視窗，以及 Anthropic 稱為 Adaptive Thinking 的能力，官方定位是「專為長程代理任務（long-horizon agentic work）所設計」。

說實話，這個定位讓我停下來認真思考了。我們團隊目前有 8 位工程師，大約在六個月前開始把 Claude Code 納入日常開發流程，那時候用的還是 Sonnet 4.x，主要用途是協助 code review 草稿、寫測試、以及處理重複性的文件任務。效果還算不錯，但「長程代理」這個層次我們還沒真正碰到過。現在 Fable 5.2 成了預設，我必須重新評估：這次升級究竟會不會改變我們的工作方式，以及我是否應該主動推動？

## 假設情境：一個 8 人後端團隊的現實盤算

讓我用具體數字描述一下我在腦中推演的情境。我們是一個 8 人後端工程團隊，負責維護一個有 15 個微服務的平台，每兩週一個 sprint，平均每週合入 20-30 個 pull request。目前 Claude Code 大約在 60% 的 PR 流程中被使用，主要集中在「幫我寫這個函數的單元測試」和「這段 code 有沒有明顯的 edge case」這類短互動。每次對話的 token 用量通常在幾千到幾萬之間，很少超過 100K。

Fable 5.2 的 1M Token 上下文意味著什麼？理論上，它可以在單次對話中讀取我們整個微服務的 codebase（每個服務約 50K–80K tokens），然後跨檔案追蹤一個 bug 的根本原因，或者自主規劃並執行一個跨多個服務的重構任務。這對我們來說是一個從「輔助工具」到「有限度自主代理」的質變轉折點。如果它真的能做到官方描述的能力，我們的 2 週 sprint 節奏可能需要重新設計。

## 身為技術經理，我會怎麼評估這次更新

### a. 對 on-call / 維運的影響

長程代理能力讓我同時感到興奮又有點擔心。興奮的是：如果 Fable 5.2 能夠在 on-call 情境下自主讀取 log、追蹤到相關的 code 路徑、然後生成一份有根據的 incident 假說，這對週末值班工程師來說是巨大的減壓。擔心的是：1M Token 的 context 代表它有能力做出更大規模的建議，甚至嘗試自動修復。我會先規定：在維運場景中，Claude Code 只能提出建議，所有 apply 動作都需要人工確認，直到我們有足夠的案例數據來評估它的判斷品質。

### b. 對 code review 流程的影響

目前我們的 code review 是人工主導，Claude Code 偶爾用來幫忙寫 review 意見草稿。Fable 5.2 的長程上下文讓它可以同時理解一個 PR 的歷史背景、相關的 issue discussion、以及被修改的所有檔案。這可能讓 AI-assisted review 的覆蓋率提高到一個新的水準。但讓我猶豫的是：如果工程師開始過度依賴 AI 生成的 review 意見，junior 工程師的 code sense 培養會受到影響嗎？這個變數我現在還沒有答案，需要在試點過程中持續觀察。

### c. 對 junior 工程師 onboarding 的影響

這裡我有比較明確的立場：1M Token 的 context 對 onboarding 是個好消息。新人通常最痛苦的部分就是「讀 codebase 讀不完，不知道改一個地方會影響哪些地方」。如果 Fable 5.2 能作為一個「有整個 codebase 記憶的技術夥伴」，幫新人解釋系統設計的歷史脈絡，我認為這有機會把 onboarding 從 3 個月壓縮到 6 週。但前提是我們要先整理出結構良好的 codebase 導覽文件，讓 AI 有好的 context 可以讀取——這本身就是一個值得做的技術文件投資。

### d. 技術債與長期維護成本

這是讓我最猶豫的面向。如果 Fable 5.2 真的能自主執行跨服務的重構，工程師可能會更容易批准「大範圍但看起來合理」的改動，而沒有真正理解每一行改動的原因。這種模式的技術債很隱性——程式碼看起來乾淨，但沒有人真的懂它為什麼那樣寫。我的應對策略是強制要求：任何由 AI 主導執行的重構，都必須伴隨一份 ADR（Architecture Decision Record），說明為什麼選擇這個方向，以及哪些替代方案被排除，才能合入主線。

### e. 採用時間軸建議

我目前的想法是分三個階段，每個階段都有明確的進場指標：

**POC（4 週）**：讓 2 位資深工程師在 feature branch 上實驗 Fable 5.2 的長程任務能力，主要觀察「從提出任務到生成可 review 的 PR 的時間」以及「第一輪 review 的修改次數」。如果相比目前流程時間縮短超過 30%，且修改次數沒有增加，就進入下一階段。

**小規模試點（8 週）**：選 2 個複雜度中等的服務，讓整個功能開發流程都允許使用 Fable 5.2 的代理模式。關鍵指標：sprint 完成率、bug 逃逸率（進 production 的 bug 數量）、以及工程師每週填寫的主觀滿意度問卷。如果 bug 逃逸率沒有上升且工程師回饋整體正面，才進入下一階段。

**全面推行**：在所有微服務啟用，同步建立針對 AI 代理操作的 code review checklist 和 ADR 要求。這個階段的衡量指標轉向更長期的技術健康度指標，例如每季的技術債清償時間。

Fable 5.2 的上線對我來說不只是「又多了一個更強的模型」，而是一個關鍵的工具鏈決策點。長程代理能力意味著 AI 開始從「助手」走向「有限度的自主協作者」，這個轉變需要的不只是工具升級，而是整個團隊對「AI 在開發流程中的角色邊界」有清晰的共識。

這是我接下來幾週會持續觀察的方向。如果你的團隊也在評估 Fable 5.2 或類似的長程代理工具，我很想知道你們在哪個環節卡住了，或者哪個假設被現實推翻了。
